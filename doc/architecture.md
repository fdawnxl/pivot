# pivot architecture

The runtime follows a one-way dependency flow from models/configuration to adapters and then to orchestration. Provider responses are converted at the boundary, so session code never imports LiteLLM types. Workspace scripts are optional runtime extensions: one broken script is logged and skipped while the rest of the workspace remains usable. Runtime modules emit English diagnostics through the central logging configuration, with independent terminal and rotating-file thresholds.

The event runtime separates generic sources from per-request conditions. Event scripts expose `-l` descriptors containing a stable name, field, supported operators, and injection templates; they do not fix a threshold. The model calls the built-in `pivot_wait_event` tool with an event, operator, expected value, and timeout. `EventService` creates a FIFO wait, polls only sources with active waiters, and returns a matched, timeout, or source-error notification as a tool message. The conversation then continues in the same bounded LLM loop. A DBus/API source belongs inside `environment/event` and can replace the sample polling implementation without changing this boundary.

Think, measure, and work scripts are all discovered through `-l` in dedicated uv projects, so workspace Python is never imported into the framework interpreter. Think scripts return their triple-quoted body through `-r` only after the model selects the summary. Measure scripts read one feature through `-r <feature>`. Work scripts accept JSON arguments on stdin through `-x` and must emit a JSON result. Subprocess timeouts, output limits, fixed working directories, and a restricted environment provide a lightweight process boundary.

Every conversation has a canonical UUID. Its JSON-lines transcript is stored atomically at `memory/<uuid>/history.jsonl` and restored when the UUID is resumed. `pivot.runtime` exposes the reusable `PivotClient` boundary independently from presentation. One-shot CLI requests keep responses on stdout and diagnostics on stderr and disk. Interactive requests use a Textual application with a persistent composer, Markdown timeline, responsive session navigation, and background session workers. Progress callbacks update one in-place agent trace containing model phases, model-provided decision summaries, capability arguments and results, event waits, and result-integration rounds. A thread-safe cancellation token adds cooperative interruption at session boundaries and during event polling without coupling the session layer to Textual. During the full-screen application, console logging is disabled so diagnostics cannot corrupt terminal rendering; structured file logging remains active.

The example measure workspace contains `virtual_sensor.py`, which starts a private `dbus-daemon`, exports `org.pivot.VirtualSensor` at `/org/pivot/VirtualSensor`, and serves `Read(feature)` through `dbus-next`. The pivot process only invokes the isolated client script, so the framework never imports the sensor dependency.
