# pivot architecture

The runtime follows a one-way dependency flow from models/configuration to adapters and then to orchestration. Provider responses are converted at the boundary, so session code never imports LiteLLM types. `ActionDetector` then normalizes native tool calls and fixed-format `<pivot-action>{JSON}</pivot-action>` output into capability, event, control, or executor actions before the session routes them. Instance scripts are optional runtime extensions: one broken script is logged and skipped while the rest of the instance remains usable.

Runtime assembly first acquires an exclusive process lease in the resolved instance. Only one process may own dependency lifecycle, the main agent, and writable runtime state for an instance at a time; a competing process fails before it starts dependencies. The lease is released during orderly shutdown and failed assembly.

Each instance owns one stable main-agent UUID. User-facing clients always submit to that agent and cannot select worker histories. `AgentControl` lets the main agent create a worker, assign an explicit subset of capabilities and events, submit a task, observe progress, and receive a structured report. Workers retain isolated histories under `memory/agents/<uuid>` and can see only themselves and the main agent through control. The combined `agent.delegate` operation performs create, assign, wait, and report in one bounded model action.

All user-facing submissions reserve a position in one main-agent FIFO mailbox before entering the control worker pool. Only the request at the head may activate the main agent; later requests remain queued and cancellation advances the mailbox safely. Worker execution bypasses this admission path because workers are owned and scheduled by the main agent.

Capabilities describe or provide domain work, while executors perform concrete machine actions. The initial `shell` executor uses a fixed instance cwd, a restricted inherited environment, a maximum timeout, and bounded output. This boundary is injectable and observable, but it remains process control rather than an operating-system sandbox.

External dependencies are standalone uv projects discovered from first-level directories under `instance/dependencies`. Runtime assembly starts valid dependencies before discovering capabilities and events, allowing those adapters to rely on already-running data sources. The dependency manager performs one initial `uv sync`, records success with an atomic `.pivot-installed` marker, and uses `uv run --no-sync` thereafter. A manifest separates the instance-local dependency id from its D-Bus bus and well-known service name. Every dependency implements `org.pivot.Dependency1` at `/org/pivot/Dependency`; heartbeat and structured status checks establish readiness without coupling pivot to the dependency's application data protocol. Installation, process, and D-Bus failures are isolated per project and retained as observable manager status.

The event runtime separates generic sources from per-request conditions. Event scripts expose `-l` descriptors containing a stable name, field, supported operators, and injection templates; they do not fix a threshold. The model calls the built-in `pivot_wait_event` tool with an event, operator, expected value, and timeout. `EventService` creates a FIFO wait, polls only sources with active waiters, and returns a matched, timeout, or source-error notification as a tool message. The conversation then continues in the same bounded LLM loop. A DBus/API source belongs inside `environment/event` and can replace the sample polling implementation without changing this boundary.

Think, measure, and work scripts are all discovered through `-l` in dedicated uv projects, so instance Python is never imported into the framework interpreter. Think scripts return their triple-quoted body through `-r` only after the model selects the summary. Measure scripts read one feature through `-r <feature>`. Work scripts accept JSON arguments on stdin through `-x` and must emit a JSON result. Subprocess timeouts, output limits, fixed working directories, and a restricted environment provide a lightweight process boundary.

The main agent and each worker have canonical UUIDs and atomically persisted JSON-lines histories. `pivot.runtime` exposes `PivotClient.run_main` independently from presentation. The Textual application shows the main timeline plus a read-only agent lifecycle sidebar. Progress callbacks update one trace containing model, capability, event, executor, control, delegation, and integration phases. A shared cancellation token propagates from the main turn into an active worker.

`pivot.control` is the shared application command surface above the runtime services. Local clients call it directly; `pivot.dbus_control` exports the same object through `org.pivot.Control1` without making CLI/TUI behavior depend on D-Bus. Fast reads are synchronous, while main-agent turns, worker delegation, capabilities, executors, event waits, and dependency lifecycle operations run as observable asynchronous control tasks. A generic operation registry makes agent and executor operations remotely available without extending the D-Bus ABI for every feature.

The example measure instance contains `virtual_sensor.py`, which starts a private `dbus-daemon`, exports `org.pivot.VirtualSensor` at `/org/pivot/VirtualSensor`, and serves `Read(feature)` through `dbus-next`. The pivot process only invokes the isolated client script, so the framework never imports the sensor dependency.
